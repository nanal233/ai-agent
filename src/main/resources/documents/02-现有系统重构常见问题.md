# 现有系统重构常见问题与解答

> 场景：系统已经在线上运行一段时间，存在历史包袱，团队正在考虑重构方案。

#### 问题一：老系统代码质量很差，但业务还在正常运转，应该推倒重来还是逐步重构？

**回答：** 绝大多数情况下，**不建议推倒重来**，应该采用**逐步重构（Strangler Fig Pattern，绞杀者模式）**的方式。原因是：

1. 推倒重来意味着新老系统在一段时间内无法同时提供业务价值，风险高度集中在"新系统上线"这一个时间点，一旦新系统有问题，可能导致业务中断；
2. 老系统里往往藏着很多"没人能说清楚为什么这么写，但删了就出问题"的隐藏逻辑（业务规则、历史补丁），推倒重来很容易遗漏这些细节；
3. 逐步重构的做法是：先把新功能用新架构实现，旧功能保持不变，通过路由或者接口层把流量逐步从旧模块切到新模块，每次只重构一小块，验证没问题再继续，风险被拆分到了很多个小的、可控的节点上。

只有在老系统的技术栈已经完全无法获得维护支持（比如用的语言/框架已经停止维护多年），或者业务规则相对简单、可以被清晰梳理，才考虑整体重写。

**推荐课程：** [《遗留系统重构实战：绞杀者模式》](https://www.google.com)

#### 问题二：重构过程中，如何保证不破坏现有业务功能？

**回答：** 核心手段是**建立自动化测试的安全网**，具体可以按下面的顺序推进：

1. **重构前，先为现有的核心业务逻辑补充测试用例**（哪怕是相对简单的集成测试），确保后续改动有一个"参照基准"，一旦改动导致行为变化，测试能第一时间发现；
2. 采用**小步提交、频繁验证**的节奏，每次只改动一个较小的范围，而不是一次性修改大量代码后才去验证；
3. 引入**灰度发布/特性开关（Feature Flag）**机制，新逻辑先只对小部分流量生效，观察一段时间没有问题后，再逐步扩大范围，最后完全替换旧逻辑；
4. 保留**快速回滚**的能力，一旦发现问题，能在很短时间内切回旧版本，减少故障影响时间。

没有测试保护的重构，本质上是在"裸奔"，风险极高，这也是为什么很多团队会把"补测试"作为重构的第一步，而不是直接开始改代码。

**推荐课程：** [《遗留代码的测试驱动重构》](https://www.google.com)

#### 问题三：系统里存在大量历史遗留的"屎山代码"，重构的优先级应该怎么排？

**回答：** 建议按照**"影响范围 × 改动频率"**这个思路来排优先级，而不是凭感觉挑"看起来最乱"的模块先动手：

- **优先级最高**：改动频率高（经常有新需求要改这块）且影响范围大（很多模块依赖它）的代码，这类代码每次改动都痛苦，重构收益最明显；
- **优先级中等**：改动频率高但影响范围小的模块，虽然收益没那么大，但重构成本也低，可以在日常开发中顺手处理；
- **优先级较低**：改动频率很低、几乎不会再改的"稳定但丑陋"的代码，即使代码质量差，重构的投入产出比也不高，可以先放着，除非它已经成为其他重构工作的阻碍。

另外要注意区分"重构"和"重写"：重构是在不改变外部行为的前提下改善代码内部结构，风险和成本都相对可控；重写则是推翻现有实现，风险更高，需要更谨慎评估。

**推荐课程：** [《代码坏味道识别与重构优先级评估》](https://www.google.com)

#### 问题四：重构时发现原有系统的数据库设计有严重问题（比如缺少索引、字段设计不合理），要不要一起改？

**回答：** 建议**将数据库结构调整和业务代码重构分开、分阶段进行**，不要在同一次改动里把两者混在一起，原因是：

1. 数据库结构变更（尤其是线上有数据的表）本身风险就比代码重构更高，一旦操作失误可能导致数据丢失或者服务中断，需要更谨慎的方案（比如灰度迁移、双写过渡期）；
2. 如果把代码重构和数据库变更揉在一起做，一旦出问题，很难快速定位到底是代码逻辑的问题还是数据库结构变更导致的问题，排查成本会显著增加；
3. 更稳妥的顺序通常是：先在不改变数据库结构的前提下重构代码（比如先优化 SQL 写法、加缓存），验证效果后，再单独规划一次数据库结构调整（比如加索引、拆表、迁移字段），并配合灰度和监控。

对于必须要做的数据库结构调整（比如严重缺失的索引导致性能问题），可以优先做**风险最低的部分**（比如加索引，通常不影响现有数据），而**涉及字段类型变更、表结构调整**这类高风险操作，则应该单独规划、充分测试后再执行。

**推荐课程：** [《线上数据库变更的安全操作实践》](https://www.google.com)

#### 问题五：团队人手有限，业务方又不断有新需求，如何说服业务方留出时间做重构？

**回答：** 这是一个很典型的"技术债"沟通问题，建议从**业务语言**而不是"技术语言"去说服业务方，具体可以尝试：

1. **把技术债翻译成业务影响**：不要说"这段代码很乱需要重构"，而是说"当前这块代码的问题导致每次需求交付时间会额外增加 X 天，且上线后 bug 率明显偏高，如果不处理，未来交付速度会持续下降"；
2. **提供量化数据**：比如统计近几个月因为这块代码质量问题导致的线上故障次数、修复耗时，用数据说话比主观描述更有说服力；
3. **提出"小步快跑"的方案，而不是要求整体停工重构**：告诉业务方不需要暂停所有新需求，而是"每个迭代拿出 20% 的时间做技术债务偿还"，这种渐进式的方案通常更容易被业务方接受；
4. **将重构和即将到来的新需求绑定**：如果业务方近期有一个需求恰好会涉及到这块烂代码，可以借这个机会，在实现新需求的同时顺带完成重构，这样重构的成本可以算在新需求的工期里，而不需要单独申请时间。

**推荐课程：** [《技术债管理与向业务方沟通的方法》](https://www.google.com)
