# 性能与扩展性瓶颈常见问题与解答

> 场景：系统已经上线运行，出现明显的性能瓶颈或扩展性问题，需要针对性优化。

#### 问题一：接口响应时间变慢，第一步应该怎么排查？

**回答：** 不要一上来就猜测原因、直接改代码，而是应该先**用监控数据定位瓶颈所在的层级**，推荐按下面的顺序排查：

1. **先看整体链路耗时分布**：通过 APM 工具（如 SkyWalking、Pinpoint）或者简单的日志埋点，确认耗时具体发生在哪一层——是数据库查询慢、是外部接口调用慢，还是应用自身的计算逻辑慢；
2. **如果是数据库层面慢**：检查慢查询日志，看是否存在缺失索引、全表扫描、锁等待等问题；
3. **如果是外部接口调用慢**：检查这个外部依赖本身的响应时间，以及是否设置了合理的超时时间和降级策略，避免被一个慢接口拖垮整个链路；
4. **如果是应用自身计算慢**：用 Profiler 工具（如 JProfiler、Arthas）分析具体是哪个方法耗时最多，而不是凭经验猜测。

排查性能问题最忌讳"拍脑袋猜原因就动手优化"，往往优化了半天却没优化在真正的瓶颈点上，浪费大量时间。

**推荐课程：** [《线上性能问题排查实战》](https://www.google.com)

#### 问题二：数据库是性能瓶颈，应该先加缓存还是先做索引优化？

**回答：** 一般建议**先做索引优化，再考虑加缓存**，原因是：

1. 索引优化的成本相对较低（通常只是加一个索引），且能从根本上解决"查询本身效率低"的问题，是性价比最高的第一步；
2. 加缓存虽然能有效降低数据库压力，但会引入新的复杂度，比如**缓存一致性问题**（数据库数据变了，缓存没有及时更新）、**缓存穿透/击穿/雪崩**等问题，需要额外的设计和维护成本；
3. 如果索引优化后，查询本身已经足够快，但是**访问量本身就是数据库扛不住的量级**（比如高并发读请求），这时候再考虑引入缓存（如 Redis）来分担数据库压力，会更有针对性。

简单来说：**先把"查询效率"这个基础问题解决好，再考虑用缓存解决"访问量"的问题**，避免在查询效率本身很差的情况下，用缓存去"掩盖"这个根本问题。

**推荐课程：** [《MySQL 索引原理与调优实战》](https://www.google.com)

#### 问题三：单机部署已经无法支撑当前流量，是该做垂直扩容（升级机器配置）还是水平扩容（加机器）？

**回答：** 需要结合成本和架构现状综合判断：

- **垂直扩容（升级 CPU/内存/磁盘）**：实施简单、几乎不需要改动代码，适合作为**短期应急方案**，但存在明显的天花板（机器配置总有上限），且成本增长通常不是线性的（越高端的机器，单位性能的成本越贵）；
- **水平扩容（增加机器数量，做负载均衡）**：能够支撑更大规模的增长，且理论上没有明显上限，但前提是你的应用必须是**无状态的**（比如不能把用户会话直接存在单台机器的内存里），否则加机器之后请求路由到不同机器会导致状态丢失的问题。

建议的路径是：**先确认应用是否已经做到无状态化**（比如把 Session 存到 Redis 而不是本地内存），如果还没有，这是做水平扩容前必须先解决的问题；如果时间紧迫、无状态化改造还没完成，可以先用垂直扩容或者简单加几台机器 + 会话粘滞（Sticky Session）过渡，但要清楚这只是临时方案。

**推荐课程：** [《分布式系统的无状态化改造实践》](https://www.google.com)

#### 问题四：引入消息队列做异步解耦和削峰，会不会让系统变得更复杂、更难排查问题？

**回答：** 会，这是一个需要正视的**权衡（Trade-off）**，不是"只有好处没有坏处"的选择，具体体现在：

1. **好处**：消息队列能有效解耦上下游系统（上游不需要等下游处理完才返回），并且在流量高峰时可以先把请求"缓存"进队列，让下游按自己的处理能力平稳消费，避免被瞬时流量打垮；
2. **代价**：引入了额外的组件（消息队列本身也需要维护、监控），业务流程从"同步调用、出错立刻知道"变成了"异步处理、出错需要专门的补偿和重试机制"，排查问题时也从"看一条调用链"变成了"要跨系统追踪消息的生产和消费"，对监控和链路追踪的要求更高。

建议只在**确实有明确的削峰填谷需求**（比如秒杀场景）、或者**上下游系统需要解耦**（比如下单后的通知、日志记录等非核心链路）时引入消息队列，而不是为了"看起来更高级"而盲目引入。同时要配套建设好**消息追踪、死信队列监控、消费失败重试**等机制，否则出问题时会比同步调用更难排查。

**推荐课程：** [《消息队列架构设计与常见坑》](https://www.google.com)

#### 问题五：系统流量存在明显的高峰低谷（比如白天流量大，凌晨几乎没有流量），资源该怎么配置更合理？

**回答：** 这种场景比较适合引入**弹性伸缩（Auto Scaling）**的思路，而不是按最高峰的流量一直保持固定数量的资源：

1. **如果是部署在公有云上**：可以配置基于 CPU 使用率、请求量等指标的自动扩缩容策略，在流量高峰时自动增加实例数量，低谷时自动缩减，既保证了高峰时的服务能力，也避免了低谷时资源的浪费；
2. **如果是自建机房、无法做到实时弹性伸缩**：可以按照"日常流量 + 一定冗余"来配置资源，应对突发的高峰（比如大促活动）则需要提前规划、提前扩容，而不是等流量已经上来了才手忙脚乱加资源；
3. 另外，也要结合业务实际情况判断"高峰低谷差异"是否值得投入弹性伸缩的复杂度——如果流量峰谷差异不大，或者业务体量本身不大，固定资源配置反而更简单可靠，没必要为了理论上的"资源利用率最优"引入不必要的复杂度。

核心原则是：**资源配置要匹配实际的流量曲线，而不是一刀切地按峰值配置或者按平均值配置**，同时要考虑团队的运维能力是否能撑得起弹性伸缩带来的额外复杂度。

**推荐课程：** [《云原生弹性伸缩架构实践》](https://www.google.com)
