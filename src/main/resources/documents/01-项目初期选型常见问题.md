# 项目初期选型常见问题与解答

> 场景：项目刚启动，团队需要确定技术栈、架构风格和基础设施方案。

#### 问题一：小团队（3人以内）做一个新项目，应该优先选择单体架构还是微服务架构？

**回答：** 对于 3 人以内的小团队，绝大多数情况下应该优先选择**单体架构**，而不是一开始就上微服务。原因有三点：

1. 微服务本身会引入服务拆分、服务间通信、分布式事务、统一日志/监控等一整套额外的复杂度，这些复杂度需要专门的人力去维护，小团队很难兼顾业务开发和基础设施建设；
2. 项目初期业务模型往往还不稳定，过早拆分服务边界，后期很可能因为需求变化需要频繁调整边界，重构成本比在单体里调整模块划分要高得多；
3. 单体架构配合良好的模块化设计（比如按领域划分包结构），完全可以在未来业务量增长、团队扩张之后，再逐步拆分成微服务，这种"先合后分"的路径风险远低于"一开始就分"。

建议：先用单体架构把业务跑通，同时在代码层面做好模块边界的划分（比如用 Maven 多模块或者清晰的包结构），为未来可能的拆分留好余地。

**推荐课程：** [《单体架构到微服务演进实战》](https://www.google.com)

#### 问题二：新项目该选择关系型数据库还是 NoSQL 数据库？

**回答：** 这个问题没有统一答案，取决于你的数据模型和查询模式，但可以按下面的思路快速判断：

- 如果你的业务数据**结构清晰、字段固定、存在大量关联查询**（比如订单要关联用户、商品、支付记录），优先选择关系型数据库（如 MySQL、PostgreSQL），因为它天然支持事务和复杂 JOIN 查询，能保证数据一致性；
- 如果你的业务数据**结构松散、字段经常变化**（比如日志、用户行为埋点、内容管理系统的动态表单），或者**读写量极大、对水平扩展要求高**，可以考虑 NoSQL（如 MongoDB 存文档型数据，Redis 做缓存/会话存储，Elasticsearch 做全文检索）。

对绝大多数新项目而言，**先用一个成熟的关系型数据库把核心业务跑起来，再根据具体场景按需引入 NoSQL 作为补充**，是风险最低的路径，而不是一上来就用多种数据库堆砌"看起来很先进"的架构。

**推荐课程：** [《数据库选型与建模实战》](https://www.google.com)

#### 问题三：团队对某个新框架不熟悉，但这个框架看起来更"先进"，该不该冒险选用？

**回答：** 需要综合评估"学习成本"和"项目工期压力"，而不是单纯看框架是否"先进"。可以问自己几个问题：

1. 项目的交付时间是否紧张？如果时间紧，选用团队不熟悉的新框架，大概率会在踩坑和查文档上浪费大量时间，风险很高；
2. 这个新框架是否有足够成熟的社区和文档支持？如果是刚发布不久、生态还不完善的框架，遇到问题很难找到解决方案；
3. 团队是否有"容错空间"？如果这是一个内部工具或者非核心业务，可以适当用来练手和积累经验；如果是核心业务系统，建议优先选择团队更熟悉、更成熟稳定的技术栈。

一个折中的做法是：**在非核心模块或者内部小工具里先试用新框架，积累经验后再考虑在核心业务中推广**，而不是直接在整个新项目的核心链路上"赌"一个团队不熟悉的技术。

**推荐课程：** [《技术选型决策方法论》](https://www.google.com)

#### 问题四：项目预期用户量不确定，架构设计要不要提前考虑高并发？

**回答：** 不建议在用户量和业务场景都不确定的情况下，过度设计"面向未来高并发"的架构。这是很多团队容易踩的一个坑，叫**过度工程化（Over-Engineering）**。

更合理的做法是：

1. 先按照**当前明确的业务需求**设计架构，保证代码结构清晰、模块职责单一，这样即使未来需要扩容，重构的成本也是可控的；
2. 在架构里预留一些"低成本的可扩展点"，比如把可能成为瓶颈的模块（如文件存储、消息通知）通过接口抽象出来，方便未来替换具体实现，而不需要为每个模块都实现"理论上支持百万并发"的复杂方案；
3. 真正遇到并发瓶颈时，再针对具体的瓶颈点做优化（比如加缓存、做读写分离、引入消息队列削峰），这样优化是有的放矢的，而不是凭空猜测未来可能遇到什么问题。

**推荐课程：** [《互联网架构演进与容量规划》](https://www.google.com)

#### 问题五：前后端该选择前后端分离，还是服务端渲染（SSR）？

**回答：** 这取决于你的产品形态和团队分工：

- 如果项目是**内部管理系统、中后台应用**，团队里前后端人员分工明确，选择**前后端分离**（比如 Vue/React + Spring Boot REST API）更合适，开发效率高，前后端可以并行推进；
- 如果项目**对首屏加载速度、SEO 要求较高**（比如面向公众的内容型网站、电商首页），应该考虑**服务端渲染（SSR）**方案（比如 Next.js、Nuxt.js），因为纯前端渲染在这些场景下首屏体验和搜索引擎抓取效果通常较差；
- 如果团队人手有限、只有一两个全栈开发者，也可以考虑**服务端模板渲染**这种更传统、更简单的方式（比如 Thymeleaf），减少前后端联调和维护两套技术栈的成本。

选型的核心不是"哪个更先进"，而是"哪个更匹配你的团队分工和产品对性能/体验的实际要求"。

**推荐课程：** [《前后端架构模式对比与选型》](https://www.google.com)
